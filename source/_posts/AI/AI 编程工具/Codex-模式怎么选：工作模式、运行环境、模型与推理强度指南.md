Codex 里的“模式”并不只代表一个开关。工作模式决定先规划还是直接执行，运行环境决定代码在哪里修改，模型决定能力、速度和成本的取舍，推理强度则决定一次任务投入多少计算资源。

对大多数开发任务，一套实用的起点是：**默认模式 + Terra Medium**。小改动可以直接在 Local 中完成；正式功能或并行任务优先放进 Worktree；只有真正困难的任务才需要 Astra、Max 或 Ultra。

> 本文核对时间为 2026 年 9 月 10 日。Codex 的模型名称、账号可用选项和界面位置可能随套餐与灰度发布变化，应以当前客户端和 OpenAI 官方文档为准。

## 先区分四个维度

选择 Codex 配置时，可以依次回答四个问题：

1. 需求是否足够明确，可以立即实施？
2. 改动应直接进入当前目录，还是需要隔离或远程运行？
3. 任务需要多强的模型能力？
4. 模型需要投入多少推理资源，是否值得拆分为并行子任务？

这四项相互独立。例如，Plan 模式可以搭配 Terra，也可以搭配 Astra；Worktree 是代码隔离方式，并不意味着模型会自动变强；Ultra 代表并行代理工作流，也不等于单个模型思考得最深。

## 工作模式：默认模式与 Plan 模式

| 模式 | 主要作用 | 适合场景 |
| --- | --- | --- |
| 默认模式 | 直接检查文件、修改代码、运行命令和测试 | 需求明确的修复、实现与重构 |
| Plan 模式 | 先调查代码、澄清约束、比较方案并形成计划 | 架构调整、跨模块改造、需求模糊或高风险变更 |

### 什么时候直接使用默认模式

以下任务通常不需要单独规划：

- 修改明确的样式或文案；
- 修复已有测试覆盖的单点问题；
- 实现接口和验收标准都清楚的小功能；
- 执行格式化、类型修正或机械性迁移。

这类任务可以直接说明修改范围、完成标准和验证命令，让 Codex 实施并检查结果。

### 什么时候先使用 Plan 模式

以下情况值得先制定计划：

- 涉及数据库结构或数据迁移；
- 修改公共 API、认证、权限或缓存策略；
- 横跨多个服务、模块或代码仓库；
- 问题根因尚不清楚；
- 存在兼容性、回滚或安全风险；
- 有多种可行方案，需要先比较取舍。

计划确认后，可以切回默认模式并给出明确指令：

```text
按刚才推荐的方案完整实施并验证。
持续处理直到相关测试和类型检查通过；如果遇到阻塞，先完成不受影响的部分，再说明具体阻塞点。
```

Plan 模式是一种“先设计、后执行”的协作流程，并不是更高档的模型。已经非常明确的小改动如果仍进行长时间规划，通常只会增加等待和上下文消耗。

## 运行环境：Local、Worktree 与 Cloud

OpenAI 将运行环境区分为 Local、Worktree 和 Cloud：Local 直接操作当前项目目录，Worktree 使用 Git 工作树隔离修改，Cloud 则在配置好的远程环境中运行。Local 和 Worktree 都在当前电脑或它连接的开发环境中执行。参见 [OpenAI 官方 Codex 环境说明](https://learn.chatgpt.com/docs/environments/modes)。

| 环境 | 特点 | 推荐场景 |
| --- | --- | --- |
| Local | 直接操作当前打开的项目目录 | 小改动、即时调试、需要使用当前本地状态 |
| Worktree | 创建隔离的 Git 工作区 | 正式功能、较大重构、多个任务并行 |
| Cloud | 在远程容器中检出并运行仓库 | 长时间任务、标准化环境、后台执行 |

### Local：前台工作区

Local 的优势是直接、快速，并且能立刻使用当前目录中的依赖、未提交文件和本地服务。它适合短小、串行、需要即时观察结果的工作。

它的代价是 Codex 与人工操作共享同一工作目录。如果同时运行多个任务，修改、依赖安装和分支切换可能相互干扰。

### Worktree：隔离并行修改

Worktree 为同一个 Git 仓库创建独立检出目录，每个任务可以拥有自己的文件和分支状态，同时共享 Git 元数据。它适合：

1. 让 Codex 在后台开发，而自己继续使用 Local；
2. 同时运行多个互不依赖的功能任务；
3. 完成后再把任务交接回 Local，进行人工检查或联调。

Worktree 依赖 Git，因此不能用于未纳入 Git 管理的普通目录。详细流程参见 [OpenAI 官方 Worktree 说明](https://learn.chatgpt.com/docs/environments/git-worktrees)。

### Cloud：远程容器执行

Cloud 会检出指定仓库和版本，运行环境安装脚本，再由 Codex 编辑代码、执行命令并展示最终差异。它适合不依赖本机专用软件的长时间任务，以及需要可重复构建环境的工作。

复杂项目应提前配置依赖、工具、环境变量和维护脚本。云端代理阶段默认的网络权限也可能受到限制，不能假设它与本机网络完全相同。参见 [OpenAI 官方 Cloud 环境说明](https://learn.chatgpt.com/docs/environments/cloud-environment)。

## 模型：Astra、Sol、Terra 与 Luna

| 模型 | 定位 | 建议用途 |
| --- | --- | --- |
| GPT-6 Astra | 综合能力最强，擅长跨代码、应用和研究的多步骤任务 | 大型重构、疑难问题、关键审查、复杂研究 |
| GPT-5.6 Sol | 强调深度、判断和完成度 | 复杂编码、开放式需求、研究和高质量文档 |
| GPT-5.6 Terra | 能力、速度和用量较均衡 | 日常开发的首选 |
| GPT-5.6 Luna | 快速、经济，适合目标清晰的重复工作 | 批量修改、提取、分类、转换和简单脚本 |

OpenAI 的当前建议是：Astra 面向最困难的端到端工作，Sol 面向复杂开放任务，Terra 面向日常工作，Luna 面向明确可重复任务。实际可见的模型会受到套餐、登录方式、客户端版本和发布阶段影响。参见 [OpenAI 官方 Codex 模型选择说明](https://learn.chatgpt.com/docs/models)。

可以用任务描述快速判断：

- “把按钮颜色改成主题变量”可以使用 Luna 或 Terra；
- “实现一个定义清楚的 REST 接口”通常使用 Terra；
- “定位偶发的并发错误”可以使用 Sol；
- “重构整个权限系统并保持迁移兼容”适合 Astra；
- “审计陌生的大型项目并给出落地方案”适合 Astra。

GPT-5.5 属于上一代模型。已有任务可以继续使用，但新任务通常优先从 Astra 或 GPT-5.6 系列中选择。

## 推理强度：Light 到 Ultra

推理强度控制模型在回答或行动前投入多少推理资源。更高强度可能改善复杂任务的结果，但也需要更多时间和用量。官方建议从默认档开始，只在任务确实需要更深入的计划、分析或检查时逐步提高。

| 强度 | 推荐用途 |
| --- | --- |
| Light / Low | 单文件小改、明确问答、格式调整 |
| Medium | 日常开发、常规调试、普通功能 |
| High | 多文件修改、复杂 Bug、重要代码审查 |
| Extra High | 架构问题、疑难故障、多约束决策 |
| Max | 最困难、需要单个模型长时间深入推理的问题 |
| Ultra | 可以拆成多个独立部分、适合多个子代理并行的大型任务 |

### Max 与 Ultra 的区别

Max 让当前模型针对单个任务投入更多推理时间，适合深度比速度更重要、但任务本身不容易拆分的问题。

Ultra 会让多个子代理分别处理复杂任务的不同部分，再汇总结果。它适合并行调查多个模块、比较多个方案或实施相互独立的工作包。如果任务只能严格串行推进，Ultra 的协调成本可能抵消并行收益。OpenAI 也明确指出，多数任务并不需要 Max 或 Ultra。

## 常见任务的推荐组合

| 任务 | 推荐组合 |
| --- | --- |
| 小型明确修改 | 默认模式 + Terra/Luna Light + Local |
| 常规功能开发 | 默认模式 + Terra Medium + Worktree |
| 中等复杂 Bug | 默认模式 + Sol High + Worktree |
| 跨模块重构 | Plan + Sol/Astra High，确认后执行 |
| 高风险架构迁移 | Plan + Astra Extra High/Max + Worktree |
| 大型代码库并行调查 | Astra Ultra + Worktree |
| 长时间后台任务 | Sol/Astra Medium/High + Cloud |

在没有历史经验时，可以把下面的比例当作个人使用基线，而不是官方硬规则：

- 约 80% 的日常任务使用 Terra Medium；
- 约 15% 的复杂任务使用 Sol High；
- 约 5% 的关键难题使用 Astra、Max 或 Ultra。

如果常用任务在更低档已经稳定得到正确结果，就没有必要长期维持最高推理强度。

## 比选择模型更重要的任务描述

高效提示应至少说明五项内容：

1. 目标是什么；
2. 哪些文件或模块在范围内；
3. 哪些内容不能改变；
4. 什么状态算完成；
5. 需要运行哪些验证。

例如，一个明确的修复任务可以这样写：

```text
修复用户退出后仍能访问 /dashboard 的问题。

范围：
- 检查前端路由守卫和服务端 session 校验
- 不改变现有登录 API
- 保持当前错误响应格式

完成标准：
- 退出后访问受保护页面会跳转到 /login
- 补充必要测试
- 运行相关测试和类型检查
- 发现关联问题可以一并修复，但在结果中说明
```

对于复杂问题，可以先要求 Codex 形成可评审方案：

```text
先使用 Plan 模式调查当前认证流程。

请输出：
- 请求链路
- 根因或设计缺陷
- 可选方案及风险
- 推荐实施步骤
- 需要修改的文件
- 验证和回滚方案

暂时不要实施。
```

任务描述越具体，Codex 越少在范围判断和反复确认上消耗时间。对重复出现的仓库规范，可以放进 `AGENTS.md`；对固定工作流，可以封装为 Skill；对周期性检查，可以使用计划任务，而不必在每次对话里重新解释。

## 一套可长期使用的默认策略

日常使用可以遵循以下顺序：

1. 需求明确就直接执行，需求模糊或风险较高就先进入 Plan 模式；
2. 普通工作从 Terra Medium 开始，复杂开放任务再切到 Sol High；
3. 只有关键且真正困难的任务才使用 Astra 或 Max；
4. 只有任务能自然拆成多个有意义的部分时才使用 Ultra；
5. 小型串行修改使用 Local，正式代码改动和并行工作优先使用 Worktree；
6. 长时间且不依赖本机状态的任务可以交给 Cloud；
7. 为每个任务写清范围、完成标准和验证命令。

核心原则是：**使用能够稳定完成任务的最低模型与推理强度，把额外计算资源留给真正困难的判断和验证。**
